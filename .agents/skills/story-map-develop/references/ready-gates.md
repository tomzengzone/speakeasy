# User Story 和 Child Vertical Slice 就绪参考

仅在创建、语义重写、拆分、合并或批准 User Story/Child Vertical Slice 时读取本 reference。

## 统一定义

- User Story 是一个连贯用户价值场景的父级容器。其 `description` 必须说明用户、使用情境、业务对象、用户目标和可见价值；它不是页面、模块、需求清单或实现任务。
- Child Vertical Slice 是 User Story 下，相对于既有能力或已显式说明的自然业务前置能力，由用户触发、选择或业务决策启动，产生一个聚焦且可观察的用户或业务结果，并可在一次正常交付迭代内完成和验证的最小端到端增量。
- “相对独立”不等于没有任何前置条件。自然业务前置关系可以存在；前置能力可用后，每个 Child Vertical Slice 必须产生自己的增量结果并可单独验收。依赖先后本身既不使 sibling 无效，也不要求把它们合并。
- “端到端”表示兑现一个增量结果所需的产品路径完整，不表示必须囊括同一 Story 的所有选择、结果、异常和技术层。不得以端到端为由制造包含多个可分别交付结果的巨型 Child Vertical Slice。

## 均衡判定维度

判断边界时必须综合以下维度，不得用任一单项机械决定拆分或合并：

1. **用户与情境**：明确谁在什么情境下获得增量；不同角色或情境只有在改变结果或边界时才支持拆分。
2. **触发与选择**：明确入口、触发事件、用户选择或业务决策；用户通过 UI 获得的新能力、选择、控制权或恢复路径可以构成产品行为。
3. **增量结果**：说明在既有或显式前置能力之上新增了什么状态、能力、决策结果或业务结果。
4. **可观察价值**：用户可以感知结果，或业务可以观察并判定结果；纯内部进展不构成价值。
5. **相对独立性**：前置能力可用后，该增量有自己的结果和验收边界，不需要另一个未交付片段共同拼成同一个基本结果。
6. **端到端完整性**：覆盖产生该增量结果所必需的产品路径和关键结果语义，但不要求机械列出或拆开每个技术层。
7. **可交付性**：可以作为有意义的产品增量交付；若暂不发布，也必须能独立集成、演示和判定完成。
8. **迭代规模**：预期可在一次正常交付迭代内完成；过大时继续按用户选择、业务规则差异、对象范围或独立结果纵向拆分。
9. **语义聚焦**：只承诺一个主要增量结果；多个可以分别交付的主要结果必须重新判断边界。
10. **可验证性**：触发或前置条件、关键选择、状态影响和可见结果足以形成稳定的端到端验证路径。
11. **恢复边界**：失败提示、重试和恢复默认跟随所属结果；只有恢复本身形成可独立选择、控制权或可观察结果时才可以单拆。
12. **事实分层**：Story Map 保留用户价值叙事和界定结果所需的产品事实，不承载详细 UI 规格、FR、TC、Contract 或实现正文。

## 拆分与合并规则

应该拆分的信号：

- 存在不同的主要增量结果，并且每个结果在其前置能力可用后都能单独交付和验证。
- 用户获得不同的能力、选择或控制权，且其中每一项都有自己的可观察结果和验收边界。
- 业务规则、对象范围、角色或情境差异导致结果语义或交付边界实质不同。
- 异常或恢复路径本身带来新的用户决策、控制权或可观察结果，而不是只支撑原结果完成。
- 当前边界超过一次正常交付迭代，并且可以沿上述产品价值维度继续纵向拆分。

应该合并或保留在同一 Child Vertical Slice 的信号：

- 拆出的部分只是同一结果的校验、加载、保存、提示、审计、通知或技术层片段，单独不产生产品结果。
- 失败、重试或恢复只负责维持原状态、解释未完成或帮助继续完成所属结果，没有形成新的用户决策、控制权或结果。
- 多个步骤必须共同完成才产生一个基本结果，任一步骤单独都只是过程进展。
- 差异只涉及布局、颜色、间距、动画参数、文案微调、组件选型或内部实现方式。

自然业务前置关系必须显式写成理解结果所需的前提，但不得仅因先后关系强制合并。反之，两个结果即使共享入口、页面、数据或技术路径，只要可以分别交付和验收，也不得仅因共享实现或“端到端完整”而合并。

## 就绪检查

User Story 就绪必须同时满足：

1. 用户、情境、目标和可见价值明确。
2. 只表达一个连贯的用户价值场景。
3. Child Vertical Slice 共同兑现 Story 承诺的价值，不引入新的独立旅程。

Child Vertical Slice 就绪必须同时满足：

1. 用户与情境、触发或选择、业务对象、增量结果和可观察价值明确。
2. 既有或显式前置能力可用后，该 Child Vertical Slice 单独完成即可形成自己的产品结果和验收边界；自然业务前置关系没有被误判为无效依赖。
3. 兑现单一增量结果所需的产品路径端到端完整，但未捆绑其他可分别交付的主要结果。
4. 可以独立交付、集成、演示和验证，颗粒度适合一次正常交付迭代。
5. 语义聚焦且验证路径稳定；触发、关键选择、状态影响和可见结果足以判定完成。
6. 用户交互按产品结果判定：形成新能力、选择、控制权或恢复路径的交互可以纳入 Child Vertical Slice；纯布局、视觉参数、组件选型或内部技术实现不得成为 Child Vertical Slice。
7. 失败与恢复默认跟随所属结果；只有形成可独立选择、控制权或结果时才单拆。
8. 关键产品边界已明确；会改变产品行为的未知项被显式保留为未决决策，详细下游事实未被复制进 Story Map。

## 信息与权威边界

Story Map 只持有 User Story 和 Child Vertical Slice 层的产品叙事。缺失行为必须保留为未决决策，不得从 Capability 名称、下游 Artifact 或通用成功/失败模式推断，也不得复制其他事实层正文来制造完整性。

界定结果所必需的用户选择、控制权、状态含义、作用范围和关键恢复事实可以保留在 Child Vertical Slice 叙事中。详细字段规则、UI 布局与视觉参数、组件选型、接口与持久化规则、技术任务、测试任务和单条验收条件应该进入适用的下游 Artifact 或实现工作，不得成为 sibling Child Vertical Slice。

普通 `draft` 只需要说明目标、已知价值或结果、必要的拆分理由和实际存在的未决决策。只有批准、语义重写、外部事实导入、事实冲突或高风险边界变化时，才需要在当前任务证据中记录适用的来源和影响范围；不得要求逐行来源分类，也不得为此增加 Story Map 字段或新 Gate。

## 正反例

以下均为方法示例，不是当前产品事实。

符合定义的示例：

- `US-0042`：内容负责人希望在内容生命周期中发布和撤回内容，使目标用户只看到当前有效内容。
- `VS-0042-1`：内容负责人完成草稿后选择发布，发布成功时内容对目标用户可见并显示已发布时间；发布未完成时草稿保持不变并可继续处理。
- `VS-0042-2`：对于已经发布的内容，内容负责人选择撤回并确认后，内容不再对目标用户可见且撤回结果明确显示。已发布内容是自然业务前置能力；该前置关系不要求与发布合并，因为撤回提供独立控制权和可观察结果。
- `VS-0042-3`：对于发布失败且草稿仍可用的内容，内容负责人可以选择修正后再次发布或放弃本次发布，并看到所选处理结果。只有当这种恢复选择被确认为独立产品能力且可单独交付时，它才适合单拆。

需要合并回所属结果或下沉的示例：

- “发布时显示进度、禁用按钮并在失败时显示错误”只支撑发布结果，没有独立选择、控制权或结果，应该保留在发布行为的下游细节中。
- “校验标题长度并显示错误”是字段规则或验收条件，不是独立价值增量。
- “调整撤回按钮颜色、间距和动画”是纯视觉参数，不是产品能力。
- “选择某个 UI 组件实现确认弹窗”是内部组件选型，不是 Child Vertical Slice。
- “实现发布 API、数据库写入和自动化测试”是水平技术任务，不是端到端用户价值。
- “编辑草稿、发布内容、撤回内容并处理全部通知”包含多个可分别交付的主要结果，不得以端到端为由合并为巨型 Child Vertical Slice。

## 就绪决定

- User Story `Id` 使用四位中性序号 `US-<NNNN>`；Child Vertical Slice `Id` 使用 `VS-<NNNN>-<N>`，其中 `<NNNN>` 与父级一致，`<N>` 是不带前导零的正自然数。所有 `Id` 必须唯一。
- Child Vertical Slice 必须嵌套在唯一 User Story 下，父子关系不使用重复字段表达。
- 记录表只包含 `Id`、`description` 和 `Status`；Capability 不决定文件、ID 或映射列。
- `draft` 表示尚未批准，不代表语义不完整；只有满足上述就绪检查且产品语义已确认时，Product Manager 才可以将其设为 `approved`。
- 发现缺失产品决策、结果重叠、水平切片、巨型 Child Vertical Slice，或前置能力可用后仍不能形成自身增量结果时，就绪结果必须为 `fail` 并说明最小阻塞项。
